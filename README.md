# Interviewer OS Frontend

Фронтенд веб-платформы для технических интервью.

Проект собран как база для реального продукта, а не как промо-страница. В текущей версии используется mock-слой на `localStorage`, но архитектура уже подготовлена под подключение реального backend API.

## Что реализовано

### Публичный вход
- единый стартовый экран;
- режим кандидата: вход по ссылке или короткому ключу;
- режим администратора: вход по логину и паролю;
- переключение языка RU / EN;
- переключение светлой и тёмной темы без перезагрузки.

### Сценарий кандидата
- вставка полной ссылки или короткого ключа;
- проверка доступа и статуса приглашения;
- запуск интервью без ввода имени;
- выбор самооценки уровня перед стартом;
- таймер запускается только после нажатия кнопки старта;
- если интервью уже начато, кандидат может вернуться по той же ссылке и продолжить;
- одна активная задача за раз;
- увеличенная рабочая область с mock IDE;
- видимые тесты, сигналы системы, ограничения и прогресс;
- после завершения показывается завершающий экран без внутренних оценок.

### Сценарий администратора
- вход: `admin / admin`;
- обзор панели;
- список участников;
- карточка участника;
- единый экран создания доступа к интервью;
- в одной форме задаются:
  - данные участника;
  - предметная область;
  - окно доступа;
  - длительность интервью;
  - доступные языки;
  - вводная и инструкции;
- после создания сразу генерируются:
  - полная ссылка;
  - короткий ключ;
- обе формы удобно копируются;
- список интервью с управлением ссылками;
- результаты;
- отчёт;
- экспорт отчёта в `txt`, `md`, `json`, `html`.

### Ключевые зоны
- `pages/public` — публичный доступ и сценарии входа;
- `pages/candidate` — кандидатский кабинет и рабочее пространство;
- `pages/admin` — админ-панель;
- `layouts` — отдельные layout для public / candidate / admin;
- `services` — сервисный слой, который легко заменить на реальные API-вызовы;
- `mock` — mock-данные и дефолтные настройки;
- `types` — доменные типы и контракты;
- `i18n` — централизованные переводы RU / EN;
- `ui` — переиспользуемые атомарные элементы интерфейса.

## Основные маршруты

### Публичные
- `/` — единый стартовый экран
- `/invite/:hash` — проверка доступа по ссылке / ключу
- `/candidate/login` — отдельный кандидатский вход
- `/employer/login` — отдельный вход администратора

### Кандидат
- `/candidate` — старт интервью и выбор уровня
- `/candidate/session/:sectionId` — рабочее пространство
- `/candidate/complete/:sectionId` — завершающий экран

### Администратор
- `/admin` — обзор
- `/admin/candidates` — список участников
- `/admin/candidates/:candidateId` — карточка участника
- `/admin/sections/create` — создание доступа к интервью
- `/admin/sections` — список интервью
- `/admin/results` — результаты
- `/admin/report/:sectionId` — отчёт
- `/admin/settings` — настройки сценария

## Как устроен mock backend

Проект не использует сервер.

Все данные хранятся в `localStorage` через сервисный слой.

### Основные коллекции
- `candidates`
- `sections`
- `results`
- `reports`
- `settings`
- `tasks`

### Где это читать и менять
- `src/services/storage.service.ts` — базовый слой хранения;
- `src/services/auth.service.ts` — вход и проверка приглашений;
- `src/services/admin.service.ts` — админские сценарии;
- `src/services/candidate.service.ts` — кандидатский сценарий;
- `src/services/interviewState.service.ts` — синхронизация статусов интервью.

## Как подключить реальный backend

### 1. Заменить реализацию сервисов
Сейчас сервисы читают и пишут данные в `localStorage`. Для реальной интеграции нужно заменить внутреннюю реализацию методов на HTTP-запросы.

Главные файлы:
- `src/services/auth.service.ts`
- `src/services/admin.service.ts`
- `src/services/candidate.service.ts`

### 2. Сохранить типы и контракты
Типы уже вынесены в `src/types`. Они могут использоваться как основа для DTO и API contracts.

Ключевые сущности:
- `Candidate`
- `Section`
- `SectionInvitation`
- `SectionResult`
- `InterviewReport`
- `Task`
- `InterviewSettings`

### 3. Что уже учтено в данных
- окно доступа к интервью отдельно от таймера прохождения;
- старт таймера только после начала интервью;
- возможность resume;
- ссылка может быть отозвана;
- уровень не задаётся администратором;
- уровень выбирает кандидат перед стартом;
- выдача задач строится по adaptive flow.

## Где менять тексты и локализацию

## Где добавлять новые страницы
- создать страницу в `src/pages/...`
- подключить её в `src/app/router.tsx`
- при необходимости добавить путь в `src/app/route-paths.ts`
- если нужен отдельный layout — использовать `src/layouts`

## Где править UX создания интервью
Главный экран этого сценария:
- `src/pages/admin/CreateSectionPage.tsx`

Именно там собраны:
- выбор нового или существующего участника;
- окно доступа;
- длительность;
- языки;
- генерация ссылки и ключа;
- копирование ссылки и ключа.

## Что важно знать про текущую логику
- участники, интервью, результаты и отчёты по умолчанию пустые;
- данные администратора: `admin / admin`;
- отдельное подтверждение имени кандидата убрано;
- вход кандидата работает только по ссылке / ключу;
- слово “секция” в основном пользовательском UX заменено на “интервью”; внутренние типы `Section` сохранены ради совместимости кода.
